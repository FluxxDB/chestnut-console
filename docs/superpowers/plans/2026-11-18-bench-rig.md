# Milestone 4 bench rig: implementation plan (PC side)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the Tab5 runs the thermostat on the real ENV III and Unit 4-Relay on Port A, with a relay-fault alert, a temperature offset set from HA, and relays that are off for certain after any fault, reset or boot.

**Architecture:** a new hardware package (`tab5-thermostat/hardware/bench-io.yaml`) provides the package-contract ids from the real parts, so the shared logic package doesn't change. The relay unit is driven by a small driver of our own: one pure C++ header (byte mapping and the link state machine, unit-tested with g++) plus thin ESPHome glue that writes all four relays as one byte and reads it back every second. A lasting failure cuts Port A's 5 V through the board's `external_5v_power` switch. HA gets a fourth alert and two System-tab controls.

**Tech Stack:** ESPHome 2026.10.1 (ESP-IDF, ESP32-P4), C++17, Home Assistant 2026.10.4, the dashboard's plain ES modules, Node 24 unit tests, pytest + Playwright e2e.

**Spec:** `docs/superpowers/specs/2026-11-18-bench-rig-design.md` (approved by Dang 2026-11-18).

## Global Constraints

- Public repo: no IPs, Wi-Fi details, keys, passwords or photos. Scripts take the Tab5's address from `TAB5_IP` only.
- No wall-screen restyle (Dang, 2026-10-29): the screen only gains the relay-fault banner line and its Paused status.
- Pinned versions stay: ESPHome 2026.10.1, HA 2026.10.4 (`docker-compose.yml`).
- Contract ids, exactly:
  - `relay_heat` = relay 1 (W), `relay_cool` = relay 2 (Y), `relay_fan` = relay 3 (G), `relay_ob` = relay 4 (O/B, never switched): template switches, `restore_mode: ALWAYS_OFF`, `internal: true`, names as in `sim/virtual-house.yaml`.
  - `relay_fault`: binary sensor, `device_class: problem`, name **"Relay Fault"** (HA: `binary_sensor.main_thermostat_relay_fault`).
  - `temperature_offset`: number, name **"Temperature Offset"**, unit `°F`, **no `device_class`** (HA in metric would convert a temperature-class number as an absolute temperature), min −5.0, max 5.0, step 0.1, initial 0, restored, `entity_category: config`. Applied to the reading in °C as `offset_f * 5 / 9`.
- Unit 4-Relay protocol: I2C 0x26; register 0x10 = mode (write 0x01: the LEDs follow the relays); register 0x11 = relays (bit 0..3 = relay 1..4; upper nibble 0).
- Link timings (spec, PC calls): fault after 5 s of failed checks; Port A cut 10 s after the fault starts; power off 3 s; 500 ms for the unit to start after power returns; retry a cut every 30 s while it doesn't answer; the fault clears after 5 s of steady answers; one check per second.
- Copy, exactly:
  - wall banner: `Relay unit not responding. Heating and cooling are paused.` Banner priority: interlock, then relay, then sensor.
  - HA alert: `Main Thermostat: relay unit not responding. Heating and cooling paused. Its power is being cycled, so a sensor fault may show too.`
  - HA cleared: `Main Thermostat: relay unit responding again.`
  - event log: on `relay unit not responding · heating and cooling paused` (kind `fault`), off `relay unit ok again`.
  - System tab: Safety row `relay unit` showing `⚠ fault` / `✓ ok`; Alerts row label `relay fault`; Device card row `temperature offset` (°F input).

## Review Focus

1. **The relay unit missing from boot** (cable out when the Tab5 starts): the Tab5 must still boot, raise the relay fault after 5 s, and keep retrying a Port A cut every 30 s, never giving up for good the way M5Stack's component does. Pinned by `link_never_answers_from_boot` (Task 2) and the boot-without-relays check (Task 7).
2. **A Port A cut while a relay is on:** after recovery the driver must send the switches' current states, not an old byte. Pinned by `link_resync_once_after_recovery` (Task 2) and the glue's "resync writes the current byte" step (Task 3).
3. **The unit answers with the wrong bits** (its chip restarted, or a write got lost): a read-back mismatch counts as not answering, is rewritten on the next check, and only becomes a fault after 5 s. Pinned by `link_brief_mismatch_no_fault` (Task 2).
4. **The offset on a metric HA:** the number must reach HA as °F, unconverted, and move the room temperature by the same °F. Pinned by `test_offset_control_writes_fahrenheit` (Task 5).
5. **A virtual-house build with the relay unit still plugged in:** Port A stays unpowered, so the unit can't hold a relay on. Pinned by `external_5v_power` becoming `ALWAYS_OFF` (Task 3) and the demo-build check (Task 7).

## Dependencies on the Mac (mac-chestnut-console)

Not planned here; ask on beacon with the spec. Tasks 4–6 wait for M1 (their contract check and e2e tests need the sim to provide the new ids).

### Task 2: The relay link (pure C++, unit-tested)

**Files:**
- Create: `tab5-thermostat/hardware/relay_unit.h`
- Create: `tools/bench/unit/test_relay_unit.cpp`, `tools/bench/test_unit.sh`

**Interfaces:**
- Produces (namespace `chestnut_hw`, header-only, no ESPHome includes):
  - `constexpr uint8_t RELAY_ADDR = 0x26, REG_MODE = 0x10, REG_RELAYS = 0x11, MODE_LEDS_FOLLOW = 0x01;`
  - `uint8_t relay_byte(bool w, bool y, bool g, bool ob);` bit 0 = W ... bit 3 = O/B, upper nibble 0.
  - `struct LinkTimes { uint32_t fault_after_ms = 5000, cut_after_ms = 10000, off_for_ms = 3000, boot_ms = 500, retry_every_ms = 30000, clear_after_ms = 5000; };`
  - `struct LinkOut { bool fault; bool port_power; bool resync; };`
  - `class RelayLink { public: explicit RelayLink(LinkTimes t = {}); void start(uint32_t now_ms); LinkOut step(bool answered, uint32_t now_ms); };` `start` = Port A was just powered; `step` once per check with whether the unit answered (write ok and read-back equal). `answered` is ignored while Port A is off and for `boot_ms` after it comes back. `resync` is true exactly once each time the unit is answering after Port A was (re)powered: the glue then rewrites the mode and relay registers.

- [ ] **Step 1: Write the failing tests** in `test_relay_unit.cpp`, in the CHECK-macro style of `tools/preview/unit/test_hist.cpp`, one block per test, times in ms from `start(0)`:
  - `relay_byte_maps_relays`: `relay_byte(1,0,0,0)==0x01`, `(0,1,0,0)==0x02`, `(0,0,1,0)==0x04`, `(0,0,0,1)==0x08`, `(0,1,1,0)==0x06`, `(1,1,1,1)==0x0F`.
  - `link_boot_resyncs_once`: `step(true,1000)` → `{fault=false, port_power=true, resync=true}`; `step(true,2000).resync==false`.
  - `link_brief_glitch_no_fault`: answers false at 1000..4000, true at 5000 → `fault==false` at every step, `port_power==true`.
  - `link_brief_mismatch_no_fault`: same as the glitch (a mismatch reaches the link as `answered=false`), true from 5000 → no fault, no resync.
  - `link_fault_after_5s`: false from 1000; `step(false,5999).fault==false`, `step(false,6000).fault==true`, `port_power==true`.
  - `link_cut_10s_after_fault`: continuing, `step(false,15999).port_power==true`, `step(false,16000).port_power==false`, `step(true,17000).port_power==false` (answers while off are ignored), `step(false,19000).port_power==true` (3 s off).
  - `link_resync_once_after_recovery`: continuing, `step(true,19400)` ignored (boot window); true at 19500..24400 → `fault==true`, no resync; `step(true,24500)` → `fault==false, resync==true`; `step(true,25500).resync==false`.
  - `link_retry_every_30s`: false from 1000 forever → power cuts at 16000, 46000, 76000; `fault==true` throughout after 6000.
  - `link_never_answers_from_boot`: `start(0)`, false from 1000 → identical to `link_retry_every_30s` (no "failed for good" state).
